# Repository work rules

- Keep `26.1.2` as the playable integration target and `26.x` as the independent 26.3/future 26.4 integration target.
- Develop each system on `feature/<target>/<system>`, as listed in `docs/foundations/FEATURE_BRANCHES.json`. Each gameplay branch must produce its own independently installable system JAR without a required TFC or sibling-system dependency; retaining the full upstream source tree for reference does not satisfy this goal. The user's 2026-10-24 instruction replaces the former no-feature-branches policy.
- Build standalone systems in independent projects under `standalone/<system>` so they never compile against the TFC source set or require another feature branch. Include the minimal local mechanics they need (e.g. cave-ins includes falling behavior). Optional integrations must remain optional. Core/build-validation lanes provide infrastructure, not pretend standalone gameplay mods.
- Preserve all gameplay, resource and registry IDs, saves, upstream credits, and EUPL notices. Do not stub out gameplay to obtain a passing build. Standalone extraction is explicitly authorized: preserve the full mod source and extract working behavior into an independent namespace/artifact, without claiming all TFC behavior was retained unless verified.
- Use the pinned libraries and a real Java 25 compiler. Read `docs/foundations/CONTINUE_BUILDING.md` and record exact validation results in the project status and work log.
- Publish scoped work on its feature branch; integrate verified work into the matching version branch. Actions quota is suspended; use `[skip ci]` until the user restores it. Run the branch-history guard plus the appropriate full build/runtime gates before integration; a history check alone does not prove source independence or playability.
- Read `docs/foundations/BRANCH_POLICY.md` for the current workflow and the historical consolidation audit. Do not rewrite existing integration history. A new branch name, skeleton build, policy change or pure algorithm test is not a completed standalone mod: require an actual JAR, dependency audit and native no-TFC launch/gameplay tests.
